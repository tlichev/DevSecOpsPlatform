DevSecOps Platform — REST API Documentation
============================================
Base URL  : http://localhost:8000/api/
API Docs  : http://localhost:8000/api/docs/      (Swagger UI)
ReDoc     : http://localhost:8000/api/redoc/
Schema    : http://localhost:8000/api/schema/    (OpenAPI 3 JSON)
Health    : http://localhost:8000/health/        (no auth)

All endpoints use JSON (Content-Type: application/json) unless stated
otherwise. Pagination is page-based: ?page=2&page_size=20.


═══════════════════════════════════════════════════════════════════════════════
AUTHENTICATION
═══════════════════════════════════════════════════════════════════════════════

The API uses JWT (JSON Web Tokens) via django-rest-framework-simplejwt.
The access token embeds role and capability flags directly in its claims
so clients do not need a separate /me/ call to check permissions.

JWT token claims (custom fields added beyond standard sub/iat/exp):
  username    string   Login username
  role        string   "admin" | "engineer" | "readonly"
  is_admin    bool     True if role==admin or is_superuser
  is_engineer bool     True if role in (admin, engineer) or is_superuser
  full_name   string   first_name + last_name

Role permission matrix across the entire API:
  Endpoint type                       readonly   engineer   admin
  ----------------------------------  ---------  ---------  -----
  GET (all read endpoints)            YES        YES        YES
  POST / PUT / PATCH (write)          NO         YES        YES
  DELETE                              NO         NO         YES
  Admin-only user management          NO         NO         YES
  AlertManager webhook (no auth)      --         --         --

───────────────────────────────────────────────────────────────────────────────

POST /api/token/
  Obtain an access + refresh token pair.

  Request body:
    {
      "username": "admin",
      "password": "secretpassword"
    }

  Response 200:
    {
      "access":  "<JWT access token>",
      "refresh": "<JWT refresh token>"
    }

  The access token expires in 8 hours. The refresh token expires in 7 days.

───────────────────────────────────────────────────────────────────────────────

POST /api/token/refresh/
  Get a new access token using a valid refresh token.

  Request body:
    { "refresh": "<JWT refresh token>" }

  Response 200:
    { "access": "<new JWT access token>" }

───────────────────────────────────────────────────────────────────────────────

POST /api/token/verify/
  Check whether a token is still valid.

  Request body:
    { "token": "<JWT access or refresh token>" }

  Response 200: {} (empty body — token is valid)
  Response 401: { "detail": "Token is invalid or expired" }

───────────────────────────────────────────────────────────────────────────────

How to authenticate requests:
  Add the Authorization header to every request:
    Authorization: Bearer <access token>

  Example:
    curl http://localhost:8000/api/devices/ \
         -H "Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9..."

DASHBOARD
═══════════════════════════════════════════════════════════════════════════════

GET /api/dashboard/stats/
  Aggregate counters displayed on the main dashboard page.
  Auth: Any authenticated user.

  Response 200:
    {
      "total_devices":   15,
      "devices_up":      12,
      "devices_down":    2,
      "devices_unknown": 1,
      "sites_online":    3,
      "active_alerts":   4,
      "critical_alerts": 1,
      "compliance_pct":  87
    }

  Fields:
    total_devices    Total registered devices
    devices_up       Devices whose status is "up"
    devices_down     Devices whose status is "down"
    devices_unknown  Devices never polled or status unknown
    sites_online     Number of distinct sites with at least one UP device
    active_alerts    Firing (unresolved) Prometheus alerts
    critical_alerts  Firing alerts with severity "critical"
    compliance_pct   Latest compliance score: pass/(pass+fail) * 100

PROVISIONING — PUSH & PULL ACTIONS
═══════════════════════════════════════════════════════════════════════════════

───────────────────────────────────────────────────────────────────────────────

POST /api/provisioning/render/
  Preview a rendered template for one device WITHOUT connecting via SSH.
  Auth: Any authenticated.

  Request body:
    {
      "device_id":     1,
      "template_name": "ssh_hardening.j2",
      "extra_context": {}
    }

  extra_context: optional dict of additional Jinja2 variables

  Response 200:
    {
      "rendered":  "ip ssh version 2\nno service telnet\n...",
      "device":    "R-Sofia",
      "template":  "ssh_hardening.j2"
    }

  Response 400: { "error": "Template 'unknown.j2' not found." }

───────────────────────────────────────────────────────────────────────────────

POST /api/provisioning/push/
  Push a rendered config to one or more devices via SSH.
  Auth: Engineer+. Enqueues on the "provisioning" queue.

  Request body:
    {
      "device_ids":    [1, 2, 3],
      "template_name": "ssh_hardening.j2",
      "dry_run":       false,
      "extra_context": { "custom_var": "value" }
    }

  device_ids:    array of Device IDs
  template_name: DB template name or .j2 file stem
  dry_run:       if true, renders the template and logs it but sends NO
                 commands to the device
  extra_context: optional additional Jinja2 variables

  Response 202:
    {
      "task_id":      "b2c3d4e5-...",
      "device_count": 3,
      "template":     "ssh_hardening.j2",
      "dry_run":      false,
      "status":       "queued"
    }

  Poll /api/provisioning/task/{task_id}/ to get the result.
  Each device gets its own sub-task in a Celery group.

───────────────────────────────────────────────────────────────────────────────

POST /provisioning/api/pull-config/
  Trigger an SSH pull of show running-config for one device.
  The config is stored in the Celery result backend (Redis) and is
  never written to disk. Auth: Engineer+.

  Note: This endpoint is mounted at /provisioning/api/pull-config/
        (under the provisioning app prefix, not /api/).

  Request body:
    { "device_id": 1 }

  Response 202:
    {
      "task_id": "c3d4e5f6-...",
      "device":  "R-Sofia",
      "status":  "queued"
    }

  Poll /api/provisioning/task/{task_id}/ until state == "SUCCESS", then:

GET /provisioning/pull-config/{task_id}/download/
  Download the running-config as a .txt file attachment.
  Auth: Login. Returns HTTP 200 with Content-Disposition: attachment.
  Filename format: {site}_{hostname}_running-config_{YYYY-MM-DD_HH-MM}.txt
  Response 202 if still running, 200 with file if done.

───────────────────────────────────────────────────────────────────────────────

GET /api/provisioning/task/{task_id}/
  Poll a Celery task result. Auth: Any authenticated.

  Response (PENDING):
    { "task_id": "abc...", "state": "PENDING" }

  Response (SUCCESS — push task):
    {
      "task_id": "abc...",
      "state":   "SUCCESS",
      "result": {
        "device":  "R-Sofia",
        "pass":    true,
        "status":  "success"
      }
    }

  Response (SUCCESS — pull-config task):
    {
      "task_id": "abc...",
      "state":   "SUCCESS",
      "result": {
        "config":    "Building configuration...\n...",
        "hostname":  "R-Sofia",
        "site":      "sofia",
        "timestamp": "2026-06-17_10-30"
      }
    }

  Response (FAILURE):

      "state":   "FAILURE",

═══════════════════════════════════════════════════════════════════════════════
WEBSOCKET — LIVE SSH TERMINAL
═══════════════════════════════════════════════════════════════════════════════

The live terminal uses Django Channels (ASGI) over WebSocket, not HTTP.

URL:     ws://localhost:8000/ws/cli/{device_pk}/
Auth:    Django session cookie (must be logged in via browser)
Role:    Engineer or Admin required
         Unauthorized → WebSocket close code 4403

───────────────────────────────────────────────────────────────────────────────

Connection flow:
  1. Client opens WS connection
  2. Server checks role → closes 4403 if unauthorized
  3. Server loads Device by pk → closes 4404 if not found
  4. Paramiko SSHClient.connect(hostname=device.ip_address, ...)
  5. channel = client.invoke_shell(term='xterm-256color', width=220, height=50)
  6. Background thread: channel.recv() → WS send
  7. Receive loop: WS message → channel.send() or resize_pty()

───────────────────────────────────────────────────────────────────────────────

Messages FROM client TO server:

  Keyboard input:
    { "type": "input", "data": "show ip route\r" }
    data: string of characters (may include special chars, arrow keys as
          escape sequences)

  Terminal resize:
    { "type": "resize", "cols": 220, "rows": 50 }
    Sent automatically by ResizeObserver when the terminal container resizes.

Messages FROM server TO client:
  Raw text data (not JSON). The terminal emulator (xterm.js) renders it
  directly. Includes ANSI escape codes, VT100 sequences, etc.

Disconnect:
  Client closes the WebSocket → server calls channel.close() and cleans up
  the background SSH reader thread.
